01先把四个核心角色分清楚

想象你坐在电脑前，对桌面助手说：“你好，简单解释一下什么是语音助手。” 几秒钟后，扬声器里传出自然的中文回答。要让这件事发生，并不是靠“一个无所不能的大模型”单打独斗，而是四个角色像接力赛一样配合完成的：

常见零基础误区：把代码下载或上传到 GitHub 只是“把菜谱存进了网盘”；要真正对话，必须在本机把服务端进程跑起来，并连上可用的模型服务。

CLIENT · 客户端

浏览器测试页 / ESP32 机器人

系统的“耳朵、嘴巴和手脚”。负责采集麦克风声音、播放服务端发回的音频，或者在收到明确指令时调用摄像头拍照、驱动底盘。

SERVER · 语音服务端

Deskbot/server/voice（我们要学透的主角）

整套系统的“总调度台”。负责接收声音、转成文字、查历史记忆、把问题交给大模型、执行工具，再把回复文字合成语音发回去。

MODEL · 大语言模型 (LLM)

只做“读文字 → 吐文字/工具请求”的大脑

关键真相：LLM 本身既听不见声音，也不能自己操作你的摄像头或读写数据库！它只能根据服务端喂给它的文字上下文，生成回复文字或写出“我想调用某某工具”的申请单。

TOOL & DB · 工具与记忆

SQLite 记忆库与 MCP 设备工具

服务端手里的“记事本”和“遥控器”。只有当 Python 程序真正查了数据库、真正向摄像头发出指令并拿到返回结果，动作才算真实发生。

餐厅后厨类比（一秒记住分工）

客户端是前台服务员（听顾客点单、端菜上桌）；server/voice 服务端是厨房总管（拆单、查忌口记录、安排工序）；LLM 大模型是只动嘴不动手的主厨顾问（看单子决定怎么答复、或开条子说“去冰柜拿食材”）；工具（MCP）才是真正跑去开冰柜拿回食材的帮厨。

02零基础拆桥：语音链路里的 4 个高频缩写

读语音 Agent 项目时，你会反复看到下面 4 个英文缩写。它们各自只干一件非常具体的事：

缩写中文全称只干哪一件事？如果这一步坏了会怎样？
VAD语音活动检测
Voice Activity Detection		判断麦克风里当前“有没有人在说话”，以及停顿多久算“一句话说完了”。切句太急会把话截成两半；切句太慢会让你说完干等很久。
ASR自动语音识别
Automatic Speech Recognition		把录下来的一段声音数据转成中文文字（俗称“语音转文字”）。如果把“打开相机”听成“打开香薰”，后面大模型收到的问题就全错了。
LLM大语言模型
Large Language Model		阅读系统提示词 + 历史记忆 + 本轮文字问题，生成回答文字或工具调用请求。答非所问、胡编乱造，或者该调工具时没调工具。
TTS语音合成
Text-to-Speech		把大模型生成的回复文字变成可播放的声音数据（俗称“文字转语音”）。网页上能看到正确的回答文字，但耳机/喇叭里完全没声音。

05对照真实源码：这些分工写在哪个文件里？

今天不需要你读懂 Python 语法符号（下一课起我们会把每个冒号、缩进、class 掰开揉碎讲）。今天只看“长什么样、职责怎么切分”——点击下方两个标签切换文件，再点击右侧编号卡片看左侧真实源码聚光灯高亮：

@dataclass(frozen=True)
class TurnRequest:
    device_id: str
    session_id: str
    turn_id: str
    text: str
    messages: list[dict[str, str]]
    device_mcp: Any | None = None
    diagnostics: dict[str, Any] | None = None


class DialogueBackend(Protocol):
    """Yield speakable text; propagate cancellation and close per-turn resources.

    Instances may serve multiple devices concurrently. Agent/tool execution
    belongs inside the backend, while audio and device messages stay in voice.
    """

    def stream(self, request: TurnRequest) -> AsyncIterator[str]: ...


class LLMDialogueBackend:
    def __init__(self, llm: LLMProvider) -> None:
        self._llm = llm

    def stream(self, request: TurnRequest) -> AsyncIterator[str]:
        return self._llm.stream(request.messages)
  1. 一轮对话的打包请求（TurnRequest）：语音层把设备 ID、转写好的用户文字 text、拼好的历史消息 messages 打包成一个干净包裹交给后端。
  2. 黄金解耦契约（DialogueBackend）：看英文注释——“Agent 与工具执行属于后端内部，音频与设备通信留在语音层”。任何后端只要接收 TurnRequest 并逐块吐出可朗读文字即可接入！
  3. 最朴素的默认后端（LLMDialogueBackend）：不开工具时，它只是把 request.messages 原样转交给语言模型流式生成回答。

06本课浓缩与深圳面试表达模板

三句话记住全局版图
  • 语音问答主干：客户端采音 → VAD 判停 → ASR 转字 → 记忆拼上下文 → 对话后端（LLM/Agent）生成回复文字 → TTS 转语音 → 客户端播放。
  • Agent 本质分工：大模型只负责“根据上下文提出工具调用请求和生成文字”，Python 宿主程序才负责“校验权限、真正执行工具并把真实回执喂回模型”。
  • 排障黄金法则：沿着数据经过的节点看证据——有文字没声音查 TTS/传输/播放；嘴上说已拍照却没画面查 tool_calls 日志与工具返回 JSON。
深圳 Agent 岗 · 30 秒项目开场介绍模板

「Deskbot 是一个支持实时语音打断、长期记忆治理与 MCP 硬件工具调用的桌面语音 Agent 系统。架构上我们通过 DialogueBackend 协议把底层的 Opus/VAD/ASR/TTS 实时音频流与上层的 Agent 决策循环彻底解耦——这既保证了语音打断时的毫秒级状态清理和底盘安全急停，又让我们能独立对 Agent 工具注册校验、错误分级自愈和混合记忆检索做纯文本自动化评测。」

07自测与通关讲回验收

可选快测：3 道职责边界判断题
1. 用户在测试网页直接打字提问，并希望听到语音朗读回答，哪一步会被直接跳过？
2. 当模型决定需要“拍照看桌面”时，是谁真正发起拍照动作的？
3. 助手回复说“我已经帮你拍好照片了”，作为开发者你怎样确认它没有撒谎（幻觉）？
🎤 面试初探追问：为什么服务端发出首个音频包的时间（first_audio_ms），不等于用户耳朵听到声音的时间？

因为服务端调用完 TTS 并把第一个 Opus 音频包写进 WebSocket 后，数据还要经过网络传输、客户端接收缓冲、Opus 解码还原以及扬声器硬件播放队列。因此工程上必须诚实区分“服务端首包耗时”与“端到端实机可听见耗时”。
